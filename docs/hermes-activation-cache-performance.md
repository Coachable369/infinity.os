# Hermes activation-cache performance pass

## Scope and acceptance boundary

The requested 50% reduction in installed desktop input-to-complete-response time is **not yet established**. Do not interpret a 1.5x speed ratio as a 50% latency reduction: halving latency requires 2x throughput on the same complete response.

This pass keeps the pinned Hermes weights, quantization, 4K context, greedy sampling, response limits, provider boundary, cancellation and worker scheduling unchanged. It does not shorten answers or substitute canned responses.

## Implementation

`kernel/runtime/ai/qwen/transformer.rs` previously called the row kernel in eight-row cooperative slices. On the single-core fallback each slice quantized the same activation vector again. `infinity_qwen_dot_rows_cached` now prepares it once at cursor zero and retains it in the engine's existing scratch buffer until that matrix completes. A new matrix or restarted/cancelled inference refreshes at cursor zero. No global activation cache, extra allocation, full-tensor dequantization or extra retained model copy is introduced.

The AP worker path already processes much larger row batches. This optimization does **not** establish a material speedup for an installed guest using those workers. That path must be measured separately before claiming the user's target is met.

## Measurement correction

The native Hermes harness previously exercised only the single-core fallback even on a multicore host. `HERMES_TEST_WORKERS` now allows it to run the production mailbox and row kernels with bounded worker threads. `hermes-response-perf.py` records both worker counts explicitly and compares identical generated bytes from binary timing receipts.

Host workers spin while idle, whereas guest APs use WFE. Consequently host worker-count experiments are diagnostic, **not justification for blindly reducing guest core counts**. The installed VM advertises FEAT_DotProd in its VirtualBox CPU feature report; lack of that feature is not its current bottleneck.

## Verification

- `tools/qwen-activation-cache-test.c`: exact cached/direct float-output equality for Q4 and Q6, widths256/3072/8192/12288, multiple row slices including a partial final slice, changed and zero activation vectors, and scratch guard preservation.
- Same test under AddressSanitizer and UndefinedBehaviorSanitizer.
- `make ai-test`: provider/runtime behavior, cancellation, concurrent worker ownership, quantized numerical references and scheduler tests.
- Complete-response performance comparisons require matching response bytes and token counts; an unfinished response at the token cap fails instead of being timed as completion.

## Repeated measurement

Five alternating baseline/candidate pairs, prompt `hello`, identical pinned weights and nine generated tokens, no host workers:

| Metric | Before | After |
| --- | ---: | ---: |
| First token | 2.0963 s | 1.3287 s |
| Complete request | 4.6154 s | 3.1033 s |
| Decode tokens/sec (8 intervals) | 3.459 | 5.507 |

This is **32.76% lower complete-request latency**, not 50%. All ten complete outputs have identical bytes. See [structured samples](evidence/hermes-activation-cache/host-paired-result.json). The VirtualBox VM and normal host applications remained running; the first repeat pair also overlapped the tail of release packaging. These are matched-workload host observations, not isolated-machine or installed-desktop acceptance numbers. Peak RAM and request-scoped CPU utilization were not re-measured for this comparison and must not be inferred from speed ratios.

`make ai-test`, the sanitizer cache test, and performance-receipt unit tests passed. The native Ministral forward test produced real output after the shared kernel change (host only). `make x86_64 aarch64` finished successfully and rebuilt both release installer ISOs in `builds/`.

Current experiment artifacts are under `builds/hermes-settings-20260924`. Installed-VM before/after measurements, complete Settings visual parity and the 50% acceptance threshold remain outstanding. The running user installation was not updated. Desktop input automation did not reliably open Command Window for guest timing diagnostics; no guest result is claimed.
