# Hermes parallel matrix queue — 2026-09-24

## Acceptance definition

The requested improvement is **75% less time from input submission to the final complete text being displayed**, on the same installed machine, model, prompt, conversation and response limits. This requires a 4x speed ratio. Host forward-pass benchmarks are diagnostic, not that acceptance result. The target remains unverified.

## Implementation

`kernel/runtime/ai/qwen/workers.rs` replaces equal fixed per-core matrix partitions with a shared atomic queue of 128-row chunks. Faster workers claim more chunks directly without asking the desktop/BSP to dispatch each chunk. Every available native AP remains eligible; no arbitrary two-core limit was introduced.

Each worker prepares its quantized activation once per matrix and reuses a private, fixed-size cache across its chunks. Workers write only uniquely claimed rows in a bounded staging buffer, never engine state or UI memory. The BSP copies results after all workers publish completion with release/acquire ordering. Matrices larger than the staging bound fall back to the existing cooperative path.

Cancellation sets a shared flag checked between chunks. A cancelled matrix is drained before staging buffers, weight ownership or a different output geometry can be reused. There are no per-token allocations, model changes, shortened answers, reduced context, capability changes or changes to final-response-only presentation.

Static memory changes: 131072 float staging rows plus 3504 floats of activation cache per worker replace 4096 private output floats per worker. For 64 mailbox slots this adds 372736 bytes, excluding tiny atomic/alignment differences. Model and KV allocations are unchanged.

## Experiments

1. BSP-driven dynamic chunk refill: three matched seven-worker host pairs improved median complete-request time by approximately 26%. Sampling still found worker waiting and BSP dispatch overhead dominant.
2. AP-claimed queue: removed per-chunk BSP dispatch. Three matched seven-worker pairs preserved exact generated bytes.
3. AP-claimed queue plus per-worker activation reuse: five matched seven-worker pairs, fixed `hello` prompt, nine output tokens, exact response-byte equality across all ten runs:

| Native-host metric | Baseline | Candidate |
| --- | ---: | ---: |
| First token | 3.4614 s | 2.3102 s |
| Complete request | 7.4222 s | 4.9530 s |
| Decode interval | 3.2340 s | 2.2295 s |

This is **33.27% less host complete-request latency**, not 75% and not installed-desktop latency. A separate two-worker comparison improved about 25.6%; it does not justify changing the guest's core count. Host worker idle behavior differs from guest WFE, and the running eight-vCPU VirtualBox VM competes with host benchmarks. The two-worker experiment also overlapped compilation; neither comparison is an isolated-machine performance claim.

The [seven-worker receipt](evidence/hermes-parallel-queue/seven-worker-host.json) and [two-worker receipt](evidence/hermes-parallel-queue/two-worker-host.json) contain all per-trial timings and matching generated-byte hashes. The [intermediate sample](evidence/hermes-parallel-queue/dynamic-host-sample.txt) is a host scheduling diagnostic, not a guest CPU-utilization report.
